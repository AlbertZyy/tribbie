# 通用分布式编号集 Halo 通信组件开发任务书

## 1. 项目目标

从零开发一个独立的 Halo 通信组件，为任意分布式编号集提供高效的数据交换能力。

组件不得绑定有限元、网格、自由度、节点或单元等具体概念。编号集中的实体只需满足：

- 每个进程持有若干本地实体；
- 实体可通过全局唯一标识符识别；
- 同一实体可以存在于多个进程；
- 可选地为每个实体指定唯一 owner；
- 实体数据的第一维对应本地实体编号。

开发工作必须包含：

1. API 与数据模型设计；
2. 阻塞和非阻塞 Halo 通信；
3. 通信计划构建；
4. 测试；
5. 基准测试与性能评估；
6. 使用文档。

本项目为独立实现，不引用或依赖任何既有实现。

---

## 2. 技术范围

### 2.1 必须支持

- Python 3.12 或更高版本；
- `mpi4py`；
- NumPy 数组；
- 任意数量的进程和稀疏邻接关系；
- 任意非连续的 64 位全局编号；
- 每个进程不同的本地实体数；
- 一个实体由两个或多个进程共享；
- 标量和多分量数据；
- 阻塞与非阻塞交换；
- `replace` 和 `sum` 两种归并语义；
- 空编号集及无邻居进程；
- 通信计划和运行期数据交换分离；
- 静态索引只在计划构建阶段交换。

### 2.2 可选支持

- `min`、`max` 归并；
- CuPy 或其他 GPU 数组；
- MPI 邻域集合通信；
- 持久化 MPI 请求；
- 自定义归并运算；
- 同一计划同时交换多个字段。

### 2.3 不在首版范围内

- 有限元装配算法；
- 网格划分；
- 负载均衡；
- 分区迁移；
- 并行文件格式；
- 全局 gather/scatter 工具；
- 容错及进程动态增减；
- 跨进程共享内存优化。

## 3. 核心设计原则

1. **算法无关**
   API 中不得出现单元、节点、自由度等具体算法概念。

2. **计划与数据分离**
   共享关系、发送索引和接收索引属于静态通信计划；数值数组属于运行期输入。

3. **稀疏邻居通信**
   运行期只能与真实邻居通信，不得使用面向全部进程的对象级 `all-to-all` 模拟 Halo。

4. **运行期不发送索引**
   索引和映射在计划构建阶段确定，重复交换时只传输数值。

5. **Typed-buffer 通信**
   使用 mpi4py 的缓冲区接口，不使用 pickle 对象通信传递运行期数据。

6. **缓冲区复用**
   避免每轮为每个邻居重复分配发送和接收缓冲区。

7. **异步生命周期明确**
   非阻塞请求完成前，发送数据、目标数据及通信缓冲区必须保持有效。

8. **确定的通信语义**
   明确定义 owner、ghost、对等副本、发送方向和归并规则。

## 4. 概念模型

### 4.1 分布式编号集

每个进程提供：

- `global_ids`：本地实体的全局唯一编号；
- 可选的 `owners`：每个本地实体的 owner rank；
- 本地编号由数组位置隐式确定。

必须检查：

- 本进程内 `global_ids` 是否唯一；
- owner rank 是否有效；
- 全局编号的数据类型是否满足要求。

### 4.2 Halo 边

一条有向 Halo 边包含：

```text
peer
send_indices
recv_indices
```

含义如下：

- `peer`：通信对端 rank；
- `send_indices`：从本地源数组打包的位置；
- `recv_indices`：接收数据写入本地目标数组的位置。

`send_indices` 与对端对应接收边的数据顺序必须一致。

### 4.3 通信模式

#### Owner-to-ghost

owner 将权威值发送给其他副本，通常采用 `replace`。

#### Ghost-to-owner

非 owner 将局部贡献发送给 owner，通常采用 `sum`。

#### Reduce-and-broadcast

分两阶段执行：

1. 所有副本贡献归并到 owner；
2. owner 将归并结果发送回所有副本。

#### Peer exchange

允许调用方直接提供有向邻接索引，不要求 owner 模型。

## 5. 目标 API

具体命名可调整，但必须保持以下能力。

### 5.1 通信计划

```python
class HaloPlan:
    @classmethod
    def from_global_ids(
        cls,
        comm,
        global_ids,
        owners,
        *,
        validation="basic",
    ) -> "HaloPlan":
        ...

    @classmethod
    def from_edges(
        cls,
        comm,
        edges,
        *,
        validation="basic",
    ) -> "HaloPlan":
        ...

    def exchange(
        self,
        src,
        dst=None,
        *,
        op="replace",
    ):
        ...

    def begin_exchange(
        self,
        src,
        dst=None,
        *,
        op="replace",
    ) -> "HaloRequest":
        ...

    def close(self) -> None:
        ...
```

### 5.2 非阻塞请求

```python
class HaloRequest:
    def wait(self):
        ...

    def test(self):
        ...

    @property
    def completed(self) -> bool:
        ...
```

### 5.3 元数据查询

计划至少提供：

- 邻居 rank；
- 每个邻居的发送和接收实体数；
- 总发送和接收实体数；
- 计划是否关闭；
- 支持的数据类型；
- 可选的估算通信字节数。

不得暴露可被调用方原地修改的内部索引和缓冲区。

## 6. API 语义要求

### 6.1 数组布局

首版约定数据形状为：

```text
(local_entity_count, ...)
```

第一维对应本地实体，后续维度全部视为每个实体的 payload。

需要支持：

- `(n,)`
- `(n, k)`
- `(n, k, m)`

同一次交换中，每个进程的 payload 形状和 dtype 必须兼容。

### 6.2 `replace`

接收值覆盖 `dst[recv_indices]`。

若多个来源写入同一位置，必须满足以下二者之一：

- 在计划验证阶段拒绝；
- 由明确、文档化的优先级决定。

首版推荐直接拒绝歧义写入。

### 6.3 `sum`

所有收到的贡献累加到目标位置。

必须明确 `dst` 原值是否参与求和。建议语义为：

```text
dst 原值保留，接收值在其上累加
```

如需从零开始归并，由调用方先清零目标位置。

重复接收索引必须正确累计，不能依赖不保证重复索引行为的高级索引赋值。

### 6.4 原地与非原地交换

- `dst=None` 表示原地更新 `src`；
- 原地交换必须先完成所有发送数据的打包，再执行可能覆盖源数据的接收写入；
- 非阻塞交换期间不得修改参与发送的数据；
- `wait()` 返回最终目标数组；
- 一个请求只能完成一次，多次 `wait()` 的行为必须明确且可测试。

### 6.5 空通信

以下情况必须合法：

- communicator 仅有一个进程；
- 本地实体数为零；
- 本进程无邻居；
- 某条边的发送或接收数量为零。

## 7. 通信计划构建

### 7.1 直接边构建

`from_edges()` 接受调用方已确定的邻接关系。实现必须验证：

- peer rank 合法；
- 本地索引不越界；
- 索引类型正确；
- 双方发送量和接收量匹配；
- 数据顺序一致或存在显式映射；
- `replace` 不产生未定义的多源写入。

### 7.2 基于全局编号构建

`from_global_ids()` 应采用分布式方法发现通信关系，不得要求每个进程持有所有进程的完整编号集。

推荐流程：

1. 根据 owner 信息确定发送方向；
2. 非 owner 将所需全局编号发送给 owner；
3. owner 将全局编号映射为本地编号；
4. 双方生成顺序一致的发送和接收索引；
5. 缓存索引及通信计数；
6. 运行期不再发送全局编号。

若首版要求调用方提供 `owners`，必须在文档中明确，不应隐式执行昂贵的全局 owner 推断。

### 7.3 验证等级

建议支持：

- `none`：仅执行运行所需的最低检查；
- `basic`：检查本地输入及通信数量；
- `full`：跨进程核对全局编号、顺序及 owner 一致性。

高成本检查只用于开发和调试，不进入性能关键路径。

## 8. 通信后端要求

### 8.1 首选实现

首版采用邻居点对点通信：

1. 对全部邻居投递 `Irecv`；
2. 打包发送缓冲区；
3. 对全部邻居投递 `Isend`；
4. 等待请求；
5. 解包并执行归并。

阻塞接口可调用非阻塞接口后立即 `wait()`。

### 8.2 通信上下文与标签

每个计划必须避免与其他计划或用户通信发生 tag 冲突。可采用：

- 独立复制的 communicator；
- 可靠的 tag 分配机制。

首版推荐每个计划使用独立 communicator，并在 `close()` 中释放。

### 8.3 缓冲区

- 按 dtype、payload 形状和邻居通信量分配；
- 在形状不变时复用；
- 若形状变化，可安全重建；
- 非阻塞请求未完成时不得复用对应缓冲区；
- 同一计划是否允许多个并发请求必须明确。

首版可禁止同一计划同时存在多个未完成请求，但必须抛出清晰异常。

### 8.4 MPI 数据类型

建立 NumPy dtype 到 MPI datatype 的可靠映射，至少支持：

- `int32`
- `int64`
- `float32`
- `float64`
- `complex64`
- `complex128`

遇到不支持的 dtype，应在通信前失败，不得静默转为 Python 对象通信。

## 9. 错误处理

至少定义并测试以下异常：

- 无效全局编号；
- 重复本地全局编号；
- 非法 owner；
- 非法 peer；
- 本地索引越界；
- 双方通信数量不一致；
- dtype 或 payload 形状不一致；
- `replace` 的多源写入冲突；
- 已关闭计划被使用；
- 同一计划出现非法并发请求；
- 请求完成前释放计划；
- 不支持的数组类型或 dtype。

跨进程验证失败时，应尽量让所有进程一致地终止当前操作，避免部分进程抛异常、其他进程永久等待。

所有 MPI 测试必须支持通过类似命令执行：


CI 至少覆盖 1、2、4 个进程。

### 12.1 单元测试

### 12.2 MPI 正确性测试

至少包括以下拓扑：

| 场景     | 进程数 | 特征        |
| ------ | --: | --------- |
| 单进程    |   1 | 无通信       |
| 两进程对称  |   2 | 双向等量      |

### 12.3 确定性测试

使用全局编号构造可预测值，例如：

```text
value(global_id, rank, component)
```

交换后通过解析公式计算期望结果，避免只比较两个可能同时错误的实现。

### 12.4 属性测试

随机生成：

- 进程邻接图；
- 全局编号；
- owner；
- 本地排列；
- 共享副本数量；
- payload 形状。

- `replace` 后 ghost 与 owner 一致；

- 本地编号排列不影响全局语义；
- 多轮交换不会积累陈旧缓冲区数据。

### 12.5 生命周期测试

覆盖：

- `test()` 未完成和完成状态；
- 重复 `wait()`；

- 请求存活期间调用 `close()`；

- 异常后计划是否仍可使用。

### 12.6 死锁防护

所有 MPI 测试配置超时。超时应被视为失败，并输出：

- rank；
- 当前阶段；
- peer；
- 请求类型；
- 通信计数。

## 13. 性能评估

### 13.1 测量指标

分别测量：

- 计划构建时间；
- 每轮打包时间；
- MPI 通信等待时间；
- 解包和归并时间；
- 总交换时间；
- 每轮发送和接收字节数；
- 临时内存峰值；
- 每轮内存分配次数；
- 非阻塞通信隐藏比例。

单轮有效 payload 为：

$$
B_p = H_pKs,
$$

其中：

- $H_p$ 为进程 $p$ 的通信实体总数；
- $K$ 为每个实体的标量数；
- $s$ 为每个标量的字节数。

有效带宽定义为：

$$
W_p = \frac{B_p}{T_p}.
$$

### 13.2 微基准

改变以下参数：

- 邻居数；
- 每邻居实体数；
- payload 分量数；
- dtype；
- 连续与随机本地索引；
- `replace` 与 `sum`；
- 阻塞与非阻塞。

每个配置必须包含：

- 预热；
- 多次重复；
- 中位数；
- 低分位和高分位；
- 跨 rank 最大耗时。

并行操作总耗时以最慢 rank 为准。

### 13.3 扩展测试

#### 弱扩展

保持每进程本地实体数、邻居数和 Halo 大小近似不变，增加进程数。

期望：

- 每轮运行时间不随总进程数线性增长；
- 运行期控制开销主要与本地邻居数相关。

#### 强扩展

保持全局问题规模不变，增加进程数。

报告：

- 总交换时间；
- 通信占总迭代时间比例；
- 加速比；
- 并行效率；
- payload 变小后延迟主导的拐点。

### 13.4 非阻塞重叠测试

构造可调节的本地计算负载：

1. 发起非阻塞交换；
2. 执行内部计算；
3. 等待；
4. 执行边界计算。

定义隐藏比例：

$$
R =
\frac{T_{\mathrm{comm}} + T_{\mathrm{compute}} - T_{\mathrm{overlap}}}
     {T_{\mathrm{comm}}}.
$$

报告不同计算量下的 $R$，并避免把纯 Python 忙循环作为唯一计算负载。

### 13.5 对照基线

至少设置：

1. 逐邻居 typed-buffer 阻塞式参考实现；
2. `Isend`/`Irecv` 加 `Waitall` 实现；
3. 当前优化实现。

如实现邻域集合通信，再增加对应基线。

不得用 Python 对象通信作为目标性能基线。

## 14. 性能验收条件

首版应满足：

- 运行期不传输全局编号或本地索引；
- 运行期不创建与 communicator 总进程数成正比的对象列表；
- 每轮通信只涉及真实邻居；
- 固定形状重复交换时复用缓冲区；
- 阻塞和非阻塞结果完全一致；
- 弱扩展中，本地邻接不变时不得出现明显的 $O(P)$ 本地工作；
- 性能报告能够区分计划构建、打包、通信和解包成本；
- 无明显的逐轮 Python 对象序列化开销。

具体时间和带宽阈值应在目标机器上建立基线后确定，不写死跨平台绝对值。

## 16. AI 智能体执行要求

智能体应按以下顺序工作：

1. 阅读本任务书并列出尚存的设计歧义；
2. 给出简短实施计划；
3. 先编写测试和最小 API 骨架；
4. 实现直接边阻塞通信；
5. 运行单元及 MPI 测试；
6. 实现非阻塞请求；
7. 实现归并和全局编号构建；
8. 运行完整测试矩阵；
9. 执行性能评估；
10. 根据 profile 优化；
11. 更新文档并提交最终报告。

每个开发阶段均需报告：

- 修改文件；
- 已实现能力；
- 执行过的命令；
- 测试结果；
- 未解决问题；
- 下一阶段计划。

不得：

- 以伪造的测试结果代替实际执行；

- 将对象级集合通信作为运行期 Halo 的默认实现；
- 将算法相关概念写入核心 API。
